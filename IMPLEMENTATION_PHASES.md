# Visual Reasoning Question Engine — Phase-Wise Implementation Procedure

This document breaks the TRD into a concrete, sequential build plan, starting from an empty repo. It's meant to be worked through with Claude Code, phase by phase — each phase has a goal, a task checklist, suggested file structure, and an exit/acceptance check before moving to the next phase.

Reference: `TRD.md` (same folder) for full requirements, data schema, and API contracts.

---

## Phase 0 — Project Setup & Foundations
**Goal:** A working repo skeleton, environment, and shared data contracts before any generator logic is written.

### Tasks
1. Initialize repo structure:
   ```
   visual-reasoning-engine/
   ├── engine/           # geometry engines (fold_punch, mirror_water, rotation_series)
   ├── render/           # image rendering (Pillow/svgwrite)
   ├── distractors/       # distractor generation per family
   ├── verify/           # VLM verification + LangGraph flow
   ├── textgen/          # LLM stem/option/explanation generation
   ├── pipeline/         # Prefect/Dagster batch orchestration
   ├── index/            # embedding index builder
   ├── api/              # FastAPI retrieval + admin service
   ├── schemas/          # shared Pydantic models (the Section 5 record schema)
   ├── data/              # local dataset store (JSONL/Parquet + images), gitignored
   ├── tests/
   │   ├── unit/
   │   ├── golden_set/
   │   └── load/
   └── scripts/          # one-off dev/admin scripts
   ```
2. Set up Python environment (poetry or venv + `requirements.txt`), pin core libs: `numpy`, `shapely`, `pillow`, `svgwrite`, `pydantic`, `fastapi`, `uvicorn`, `langgraph`, `langchain`, a vector store client (`faiss-cpu` or `chromadb`), `prefect` (or `dagster`), `pyarrow` (Parquet).
3. Define the **Record schema** (Section 5 of TRD) as a Pydantic model in `schemas/record.py` — this is the single source of truth every later component reads/writes against.
4. Set up config management for swappable model interfaces (Section 7): one interface class for "VLM provider" and one for "LLM text provider," each with a concrete implementation you can swap via config/env var. Don't wire real model calls yet — stub them.
5. Set up `data/` layout: `data/records/*.parquet` or `.jsonl`, `data/images/{question_id}/...`.
6. Basic logging/observability scaffold (structured logs) so every later phase can log into it instead of retrofitting.
7. Git init, `.gitignore` for `data/`, images, and any API keys/`.env`.

### Exit Criteria
- Repo runs `pip install` / `poetry install` cleanly.
- `schemas/record.py` importable and validated with a hand-written dummy record.
- Config loads a VLM/LLM provider name from env without erroring (stub implementations return canned output).

## Phase 1 — Fold & Punch Generator, End-to-End (MVP Vertical Slice)
**Goal:** One complete family working end-to-end — this is the hardest phase because it proves the whole pipeline shape (Lane 1 in Section 3.1). Matches TRD Phase 1.

### Tasks
1. **Parameter Sampler** (`engine/fold_punch/sampler.py`): generate valid random configs — fold axis (vertical/horizontal/diagonal), fold count (1–3), punch count (1–4) and positions. Bias sampling toward under-represented difficulty buckets (stub a uniform sampler first, refine later).
2. **Geometry Engine** (`engine/fold_punch/geometry.py`): pure NumPy/Shapely code that:
   - Computes the folded paper's coordinate transforms.
   - Computes punch positions in folded space.
   - Unfolds to get final punch-hole positions — this is the deterministic "correct answer."
   - Write unit tests first (TDD) with hand-verified fixed cases (Section 9 — geometry unit tests) before writing the general-case code.
3. **Image Renderer** (`render/fold_punch.py`): draw the question image (folded state + punch) and the correct-answer image (unfolded paper with holes), using Pillow or svgwrite.
4. **Distractor Generator** (`distractors/fold_punch.py`): produce exactly 3 wrong options, each generated by deliberately breaking one specific rule (e.g. wrong symmetry axis, missing a hole, extra hole, mirrored wrong). Tag each with the rule broken (FR-5).
5. **Difficulty tagging** (`engine/fold_punch/difficulty.py`): derive 1–5 difficulty from fold count + punch count + distractor subtlety (FR-11).
6. **VLM Verifier + LangGraph loop** (`verify/graph.py`):
   - Build a LangGraph graph: Generate → Render → Distractors → VLM Verify → conditional edge: agree → proceed to text gen; disagree → resample (up to 3 retries) → human review queue (just a flagged-records file/table for now).
   - Wire the VLM stub from Phase 0; keep it swappable per Section 7.
7. **LLM Text Generator** (`textgen/generator.py`): from the structured record, generate stem, option labels, and step-by-step explanation (distractor tags → explanation text for each wrong option) (FR-8).
8. **Persist to Dataset Store**: write each completed record (schema from Phase 0) to `data/records/` + images to `data/images/`, including `verification` and `params` fields for auditability (FR-4, FR-12).
9. Run a first real batch (small, e.g. 50–100 records) using stub or a real VLM/LLM if API keys are available.
10. Write the **golden-set** for fold_punch: freeze ~50-100 hand-verified records for regression testing (Section 9).

### Exit Criteria (matches TRD NFRs)
- ~500 verified fold_punch records generated and stored.
- Geometry unit tests pass for all fold-axis × fold-count × punch-count combinations tested.
- VLM agreement rate tracked and logged (target ≥98%, can be aspirational with a stub/small model at this stage).
- Every record traceable: params + model versions stored (auditability, Section 6).

## Phase 2 — Mirror/Water Image & Rotation/Series Generators
**Goal:** Extend the proven Phase 1 shape to the other two families, sharing code where possible. Matches TRD Phase 2.

### Tasks
1. Refactor Phase 1's geometry/render/distractor code into a **shared transform library** (`engine/common/`) where the fold/mirror/rotation math shares utilities (coordinate transforms, image compositing, distractor-rule tagging pattern) — don't duplicate boilerplate per family.
2. **Mirror/Water Image family** (FR-2):
   - `engine/mirror_water/geometry.py`: reflect a figure across vertical, horizontal, or arbitrary-angle axes.
   - Configurable figure library (start with a small set of base shapes/letters/patterns, expand later).
   - Renderer + distractor generator + difficulty tagging, following the Phase 1 pattern.
3. **Rotation/Series family** (FR-3):
   - `engine/rotation_series/geometry.py`: rotate a figure by a configurable step size across a configurable sequence length; compute the correct "next in series" answer.
   - Renderer + distractor generator + difficulty tagging.
4. **Unify the Parameter Sampler** (`engine/sampler.py`) across all three families — single entry point that samples `family` first, then family-specific params, still biased toward under-represented difficulty buckets across the whole dataset (not per-family in isolation).
5. Extend the LangGraph verify/repair flow to be family-agnostic (it should already be, if Phase 1's graph was built generically against the schema rather than hardcoded to fold_punch).
6. Extend LLM Text Generator prompts to handle all three families' explanation styles.
7. Build golden-sets for mirror_water and rotation_series (Section 9).
8. Generate a balanced first multi-family batch (e.g. 500–1000 per family) and confirm difficulty distribution isn't skewed (Section 10 risk: dataset skew).

### Exit Criteria
- All three families generate, render, verify, and persist correctly through one shared pipeline entry point.
- Golden-set regression tests exist and pass for all three families.
- Difficulty distribution report shows reasonable spread across 1–5 for each family.

## Phase 3 — Scale-Out, Orchestration, Dedup, Scanned-Book Ingestion
**Goal:** Move from "it works" to "it works at 100k+ records, reliably, unattended." Matches TRD Phase 3.

### Tasks
1. **Batch orchestration** (`pipeline/`): wrap the Lane 1 flow in Prefect (or Dagster) flows/tasks:
   - Parallel workers for parameter sampling + geometry + rendering (CPU-bound, horizontally scalable per NFR "Throughput").
   - Batched/parallelized VLM and LLM calls (these are the bottleneck per Section 6).
   - Retry policy: failed verifications retry up to 3x with resampled params before routing to human review queue (Reliability NFR) — implement this as a proper Prefect retry/branch, not ad hoc code.
2. **Dedup** (FR-10, Section 9 "Dedup validation"):
   - Add embedding-similarity dedup check before a record is considered final/indexable.
   - Write a test with deliberately near-duplicate synthetic records to confirm dedup catches them.
3. **Difficulty balancing at scale**: implement the under-represented-bucket bias as a real feedback loop reading current dataset stats (not just a static prior), so late-stage generation actively fills gaps.
4. **Scanned-book ingestion path** (FR-7):
   - Build an ingestion entry point that takes scanned question images, routes them through the same VLM verification path (VLM "solves" the scanned question), and tags `source=scanned_book`.
   - These records skip the geometry-engine step (no synthetic params) but still populate the schema (params may be null/partial) — decide and document that convention.
5. **Observability** (Section 6): implement and expose generation rate, VLM agreement rate, dedup rate, per-family/difficulty distribution, retrieval latency (retrieval latency will be wired in Phase 4, stub the metric now).
6. Storage efficiency pass: confirm images are compressed PNG/SVG, average under 50KB (NFR).
7. Run a scaled batch (start with 5k–10k records total) to validate the orchestration doesn't fall over, then plan the run to 100k+.

### Exit Criteria
- Orchestrated batch run completes unattended with automatic retry/flagging, no silent drops.
- Dedup demonstrably rejects near-duplicate test records.
- Dashboards/logs show generation rate, VLM agreement rate, dedup rate, difficulty distribution.
- At least one scanned-book record successfully ingested and verified end-to-end.

## Phase 4 — Embedding Index & Retrieval API
**Goal:** Make the verified dataset servable in real time. Matches TRD Phase 4.

### Tasks
1. **Embedding Index Builder** (`index/builder.py`, Lane 2, Section 3.2):
   - After each batch, embed each record's `embedding_text` (question text + tags — not image pixels) and write to a vector store (FAISS/Chroma/pgvector).
   - Store metadata fields alongside vectors: `family`, `sub_type`, `difficulty`, `exam_style`.
   - Make this incremental (append new batch, don't rebuild from scratch each time) once basic version works.
2. **Retrieval API** (`api/`, Lane 3, Section 3.3 + Section 8):
   - `GET /v1/questions` — metadata filter (family, difficulty range, exam_style) + vector similarity search for diversification; implement per-user/session "recently served" exclusion list (Section 10 risk mitigation).
   - `GET /v1/questions/{id}` — full record for admin/debug.
   - `POST /v1/generate` — internal/admin trigger for a new batch run (wraps the Phase 3 pipeline).
3. Auth-gate all endpoints (Section 6, Data sensitivity — DRDO/pilot-selection context).
4. **Retrieval load testing** (Section 9): simulate concurrent filtered requests, confirm p95 < 300ms for up to 20 questions returned.
5. Wire the real retrieval-latency metric into the observability stack from Phase 3.
6. Integrate with the consuming application (however that's defined outside this TRD's scope) — confirm the response shape (Section 8.2) matches what the consumer expects.

### Exit Criteria
- `/v1/questions` returns correctly filtered, deduplicated, ranked results within latency target.
- Load test confirms p95 < 300ms at target concurrency.
- Auth is enforced on all endpoints.
- At least one successful end-to-end integration call from the consuming application.

## Phase 5 — Hardening, Monitoring & Ongoing Operations
**Goal:** Not in the original phased table, but implied by Sections 6, 9, 10 — the operational tail that keeps the system trustworthy after initial delivery.

### Tasks
1. Set up alerting: VLM agreement rate drop below 98% threshold triggers an alert (signals a rendering/distractor bug — Section 9).
2. Schedule periodic human spot-checks (~1% sample) of newly verified records (Section 9), especially important right after any pipeline change.
3. Schedule periodic cross-check of a sample against a second, different VLM to catch correlated verifier blind spots (Section 10 risk).
4. Set up model-swap procedure: before switching the VLM or LLM provider, re-benchmark against the fixed held-out set (Section 7, Section 10).
5. Track dataset growth toward the 200,000-records-per-family scalability target (Section 6); revisit orchestration/storage if approaching that ceiling.
6. Document the re-render path: confirm any record can be re-rendered at a different resolution purely from stored `params`, without recomputing geometry (FR-12) — write a test proving this.
7. Revisit Appendix A open questions with the team before considering v1 "done":
   - Target dataset size per family/difficulty tier.
   - Self-hosted vs API-based VLM/LLM decision for the DRDO-context deployment.
   - Priority exam styles for the first LLM phrasing pass.

### Exit Criteria
- Alerting and spot-check cadence documented and running.
- Model-swap runbook exists and has been exercised at least once (even in a dry run).
- Open questions from Appendix A explicitly answered/decided and recorded.

## Suggested Order of Work Summary

| Phase | Focus | Depends on |
|---|---|---|
| 0 | Repo, env, schema, config | — |
| 1 | Fold & punch, full vertical slice | Phase 0 |
| 2 | Mirror/water + rotation/series | Phase 1 |
| 3 | Orchestration, scale, dedup, scanned ingestion | Phase 2 |
| 4 | Embedding index + retrieval API | Phase 3 (needs a non-trivial verified dataset to index/serve) |
| 5 | Hardening & ongoing ops | Phase 4 |

**Note for Claude Code sessions:** work one phase at a time, and don't start a phase's tasks until the previous phase's exit criteria are demonstrably met (tests passing, sample records inspected). Each family added in Phase 2 should reuse Phase 1's shared code rather than copy-pasting the fold_punch implementation — refactor into `engine/common/` as soon as the second family reveals what's actually shared.
